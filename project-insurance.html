Context

A platform built to last — maybe too long

The platform had been in production for over 10 years. Thousands of insurance agents used it daily to manage policies, claims, and client records. It worked. But it looked and felt like it was from another era — small fonts, dense tables, inconsistent button styles, and no visual hierarchy to guide the eye.

The challenge: the business couldn't afford a full rebuild. The backend was stable and deeply integrated. What they needed was a way to make the interface dramatically better without changing how the system worked underneath.

Problem

The challenge

Agents were spending extra time scanning screens because there was no clear visual priority. Critical actions (like approving a claim) sat alongside low-priority links with identical styling. The colour palette was arbitrary — there was no system behind it, just years of accumulated decisions.

On top of that, every page was a slightly different interpretation of the same interface. Forms, tables, and modals all behaved differently. Agents who moved between modules had to mentally re-learn the UI each time.

"It gets the job done, but I spend half my day looking for things that should be obvious."

— Insurance Agent, User Interview

Research

Understanding how agents actually work

I ran five contextual interviews with agents across different departments — claims, policies, and client management. I also shadowed two agents for a half-day each to watch real usage patterns. Three themes emerged that shaped every design decision:

Scanning, not reading

Agents don't read interfaces — they scan for known patterns. The existing design made every element equally loud, forcing agents to read everything to find what they needed.

Consistency reduces errors

When button placement, form layout, and table patterns are consistent across all modules, agents develop muscle memory — drastically reducing mistakes on high-stakes actions like claim approvals.

Speed is everything

Agents handle dozens of records per shift. Even saving 5 seconds per task — through better visual hierarchy and fewer clicks to find things — compounds to meaningful productivity gains across a team.

Process

How I approached the redesign

01

Audit & component inventory

I documented every UI component in the existing system — buttons, form fields, tables, modals, navigation states. This gave me a complete map of the inconsistencies and a baseline for the new design system.

02

Define the design system foundation

Before redesigning any screens, I established a consistent token system in Figma: colour palette with clear semantic meaning (primary, danger, success, neutral), typography scale, spacing units, and border radius values.

03

Redesign the highest-traffic screens first

Working with analytics data, I identified the five most-visited modules. These were redesigned first in Figma, validated with two agents in brief feedback sessions, then refined before expanding to the rest of the platform.

04

CSS/Less implementation

The platform used a Less-based stylesheet. I implemented the new design system by replacing the existing stylesheet layer — no backend changes, no template restructuring. Just a clean new CSS/Less layer applied on top of the existing HTML structure.

05

QA across browsers & edge cases

Tested across Chrome, Firefox, Edge, and IE11 (a hard requirement for this enterprise client). Identified and resolved 23 visual inconsistencies in edge-case data states — empty tables, long text overflow, multi-line form labels.

Outcome

Results

Following a phased rollout to the full agent team, the product owner shared feedback and early usage metrics:

40% reduction in time-on-task for the claim approval flow — measured via session recordings before and after
0 backend changes required — the entire transformation was delivered through the CSS/Less layer only
9 / 10 average satisfaction score from agents in a post-launch survey — up from 4/10 before the redesign

Reflection

What I learned

This project taught me that constraints are often the best design brief. Working within an unchangeable HTML structure forced me to think purely in terms of visual layer — typography, colour, spacing, and component design — which are actually the most powerful levers for perceived quality.

The design system work done upfront saved enormous time during implementation. Because every token was defined before a single screen was built, the CSS was almost mechanical to write — it was just translating decisions that had already been made.

The biggest lesson: enterprise users have strong existing mental models. Radical changes — even good ones — create friction. The right approach was to make things feel familiar but significantly cleaner, not reinvent the interaction model entirely.

If I extended this project, I'd push for an interactive prototype to test the redesigned navigation with agents before CSS implementation — some edge cases in the table interactions only became apparent once agents were clicking through a real build.
